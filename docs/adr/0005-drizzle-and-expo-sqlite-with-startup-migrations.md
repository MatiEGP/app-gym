# 0005. Drizzle ORM over expo-sqlite, with migrations applied at startup

- **Status:** Accepted
- **Date:** 2026-11-08
- **Deciders:** MatiEGP
- **Related:** [#12](https://github.com/MatiEGP/app-gym/issues/12), [ADR 0003](0003-offline-first-local-sqlite.md)

## Context and problem statement

[ADR 0003](0003-offline-first-local-sqlite.md) makes a local SQLite database the source of truth. The schema will change with every milestone (exercises, workouts, sets, routines), and each change must reach an already-installed app without losing the user's workout history. Queries should be type-checked, because a wrong column name in a set or weight field corrupts the data that matters most. How do we access SQLite and evolve its schema safely on the device?

## Decision drivers

- Type-safe queries from a schema written in TypeScript.
- Versioned migrations generated from the schema, applied automatically on the phone.
- A failed migration must never crash the app or silently continue with a broken database.
- Works with `expo-sqlite`, which ships in Expo Go and needs no extra native module.
- Light footprint and plain SQL underneath; no heavy framework.

## Considered options

1. Drizzle ORM over `expo-sqlite`, migrations generated by drizzle-kit and applied at startup
2. Raw SQL with `expo-sqlite` and hand-written migrations
3. WatermelonDB

## Decision outcome

**Chosen: Drizzle ORM over `expo-sqlite`**, because it gives a TypeScript schema and typed queries while staying close to SQL, and drizzle-kit generates migrations that Drizzle's Expo migrator applies at startup.

How it works:

- `src/shared/db/schema.ts` defines tables; `pnpm db:generate --name <change>` writes a versioned `.sql` migration plus a journal.
- Babel inlines `.sql` files and Metro resolves them, so migrations ship inside the bundle.
- `MigrationGate` wraps the app: it shows a loading state, applies pending migrations, and then renders the app, or shows a Spanish error screen if a migration fails.
- The first migration creates `app_meta`, a local-only key/value table for infrastructure data (for example, a future sync cursor). It also made the "applies pending migrations, then none" behavior verifiable before any feature table existed.

### Consequences

- **Good:** schema changes are reviewed as generated SQL in PRs and applied on every device the same way.
- **Good:** a broken migration shows an error screen instead of a crash or a half-migrated database.
- **Bad / trade-offs:** generated migrations must never be edited or deleted once merged (devices already applied them); deleting one by hand leaves the journal pointing to a missing file.
- **Bad / trade-offs:** extra build configuration (Babel inline-import, Metro `sql` extension) and generated files excluded from lint and formatting.
- **Follow-ups:** the Postgres schema in Supabase must mirror synced tables (M5).

## Pros and cons of the options

### Drizzle over expo-sqlite

- ✅ Typed schema and queries; SQL-like API.
- ✅ Generated, versioned migrations and a ready-made Expo migrator.
- ❌ Build-tool configuration for `.sql` imports.

### Raw SQL with hand-written migrations

- ✅ No dependencies beyond `expo-sqlite`.
- ❌ No type safety: column typos surface at runtime, on the phone.
- ❌ Migration tracking must be built and tested by hand.

### WatermelonDB

- ✅ Built for offline-first apps, with a sync protocol.
- ❌ Its own model layer and native module; heavier and more opinionated than needed for a single-user app.
- ❌ Its sync protocol does not fit Supabase directly; a custom outbox would still be needed.

## Evidence

- Implementation and tests (loading, success, and error states with a mocked migrator): [PR #32](https://github.com/MatiEGP/app-gym/pull/32).
- Device check: two launches both reached the app. Drizzle generates `CREATE TABLE` without `IF NOT EXISTS`, so re-applying the migration on the second launch would have shown the error screen.
- `db:generate` probes: no schema change → "No schema changes"; a temporary column → `ALTER TABLE` migration (reverted).
